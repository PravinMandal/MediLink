1. System Architecture

1.1 Overview

MediLink is a consent-gated longitudinal health record. Patients own one chart; verified doctors and labs contribute clinical data; no professional read is possible without an active, unexpired, scoped consent grant — except a time-boxed, audited emergency window. Every sensitive action is appended to a hash-chained audit log. It is a 3-tier web system, deployed serverless:

CLIENT — React Server Components (default) + small client islands
   (forms, drawers, search, theme toggle, notifications bell)
            │ HTTPS
APP SERVER — Next.js 16 App Router (Vercel, Node runtime)
   Routes (/portal/*, /api/*, /e/*) · Server Actions (mutations)
   Guards: requireUser → requireRole → requireVerifiedPractitioner
           → access.assert
   Services: consent · records · patients · documents · emergency · audit
   Worker (/api/worker + outbox jobs): extraction, notifications, re-scans
            │ SQL (Drizzle ORM)            │ signed URLs / bytes
DATA — PostgreSQL                    OBJECT STORAGE (Supabase)
   Supabase (prod) / PGlite             original PDFs/images/text,
   embedded (dev), same schema          immutable, sha-256 hashed

1.3 Key architectural decisions

  1. Server-first security. Authorization lives in access.assert() on the server. Hidden buttons and client route guards are convenience only — verified by exercising doctor URLs as a patient (bounced server-side).
  2. Consent is the addressing scheme. Reads are keyed (practitioner, patient, scopes, time-window), not just (user, row).
  3. Immutable clinical history. Corrections supersede (new version), never overwrite; disputes flag, never edit.
  4. Deterministic before probabilistic. Conflict detection and the default summary are pure functions; the LLM is an optional renderer that must cite or drop claims.
  5. Cheap by construction. One Next.js app + managed Postgres + object storage, all on free tiers. No always-on servers, no per-seat services.
  6. Dev/prod parity. PGlite runs the same Drizzle schema and migrations locally, so data-layer behavior (including the audit chain) is identical in both environments.

2.3 Relationship rules that matter

  • Grants reference practitioner.id (stable across resubmission), never the user id.
  • Dispute raising verifies the flagged row belongs to the raiser's chart (single UNION ALL over the 9 clinical tables) — cross-patient flagging is rejected.
  • conflicts.resolved_by has a user FK: human resolutions reference a user; system auto-resolutions use NULL (no fake "system" user).
  • Deletions cascade only downward (search chunks die with their row). Clinical facts are never hard-deleted.

3. Algorithm Selection

Every algorithm was chosen for auditability over cleverness — a health record must be explainable in a dispute.

3.1 Contradiction detection (deterministic rules)

DetectorRuleSeverity
Blood groupVerified lab value ≠ patient self-report; verified value displayedcritical
AllergySame substance, distinct criticality‖reaction across live rowswarning
Duplicate documentIdentical contentHash on 2+ documentsinfo
Lab valueSame analyte + same date, distinct numeric valueswarning

Each row carries a content _key (sha-256 of kind + details) so distinct analytes/allergies coexist and re-scans dedupe. Reconciliation: after every scan, open conflicts whose key was not reproduced are auto-closed with a preserved note — corrections and supersessions clear stale banners automatically. Why rules, not ML: reproducible, unit-testable, zero hallucinations, millisecond runtime.

3.2 Summarization (deterministic SBAR + cited LLM option)

Default mode is a pure function: scoped facts → SBAR structure (key events, history, recent changes, open data issues), every sentence carrying source citations. LLM mode is a renderer under the same contract: a claim without a source is dropped, recorded-fact language never implies AI judgment, and the mode badge (deterministic vs LLM · model) is always shown. A stored summary from broader consent is never shown to a narrower grantee.

3.3 Identity and access algorithms

  • Patient code ML-XXXXX-XXXXX-C: random segments plus a check character that catches typos; case/dash-insensitive normalization. Possession grants nothing.
  • Policy evaluation: scopeForResource() maps every record kind to its consent scope and throws on unknown kinds (fail-closed); emergency basis exposes a fixed critical set; revocation re-evaluated per read; every decision logged.
  • Rate limiting on discovery/lookup endpoints against enumeration.
  • Verification: mock provider auto-approves plausible registrations (demo); implausible ones queue for human review; every submission/decision audit-logged.

3.4 Retrieval

Record search runs over search_chunks (label + full text, GIN-indexed), always filtered by patient and by the reader's granted scopes; the same index supplies human labels for the concerns queue.

5. User Interface (UI) Design

5.1 Design language

  • Typography: Fraunces (display serif — editorial trust), Instrument Sans (UI), Plex Mono (codes, hashes, values).
  • Color: pine (primary trust signal), alert/amber/info statuses — every pair contrast-tested per mode (WCAG AA, axe-enforced). Glass effects only where they aid hierarchy; body-text cards are solid.
  • Shape & motion: 12–24px radii, 1px line borders, soft shadows; one Reveal scroll system (opacity/translate only) with full prefers-reduced-motion support and a view-transition theme wipe.

5.2 Themes

Daylight (default), Obsidian (dark), system-follow, plus an independent Reduce Transparency toggle — persisted, with a pre-hydration script so there is no flash. Dark mode is a separately designed palette, not an inversion (verified across 12 pages).

5.4 AI UX

Summaries render as an evidence rail: recorded-fact groups as stations on a line, each claim with inline citation chips resolving to sealed rows — visually distinct from authoritative records, with mode badge, generation timestamp, and a "verify against sources" affordance. Long responses paginate by group. Errors, empty states (honest "no record found as of this date"), and permission-denied states are all designed, not defaults.

5.5 Every-state discipline

Each workflow ships normal / loading / empty / error / partial-data / denied / expired-session / malformed-input / slow-network / mobile / both-themes — enforced by the 34-check Playwright suite, not by convention.

6.2 Integrity mechanisms

  • Fail-closed reads: every clinical query is built with the evaluated scope set — narrower consent means fewer tables touched, never client-side row filtering.
  • Idempotency: extraction retry deletes by sourceDocumentId before re-insert; break-glass arming is idempotent per live window; outbox dedupes by event key.
  • Concurrency: audit hash computed in-transaction (single pgcrypto statement in prod; serialized fallback in tests); corrections link replacesVersionId, so concurrent edits fork visibly instead of clobbering.
  • Migrations: numbered Drizzle SQL + journal, applied identically to Supabase and PGlite. Seed produces the golden chart, conflicts, SBAR summary, and demo accounts ending with chain intact ✓.

7. System Flow

7.1 Consent lifecycle (the core loop)

Doctor (verified, no access)
  │ identifier lookup (ID only — nothing leaks pre-consent)
  ▼
Access request (proposes scopes + purpose + duration)
  │ patient inbox card: who / why / which categories / how long
  ├─ Decline ──► closed + notified
  └─ Grant (patient NARROWS scopes) ──► consent {hash, receipt, expiry}
        │ doctor workspace unlocks ONLY granted scopes
        │ AccessBanner shows purpose · scopes · exact expiry
        ├─ Renew ──► fresh request before expiry
        └─ Revoke ──► immediate; next read denied + audited

7.2 Lab contribution → citation

Lab uploads original (consented patient only)
  → magic-byte validation, ≤ 4 MB → bytes stored immutable + sha-256
  → worker extracts observations → structured rows (trust = extracted)
  → attestation (doctor/lab reviews, seals a version)
  → contradiction re-scan → indexed into search_chunks
  → summary cites it (claim ↔ sealed row, page-level)

7.3 Emergency (break-glass)

Unresponsive patient → verified doctor opens Emergency access
  → enters Patient ID + clinical reason + own password (step-up)
  → ONE 60-minute window (idempotent) → critical scopes only
  → every read audited → patient notified → admin reviews afterwards

7.4 Dispute loop

Patient flags a row in a provenance drawer (chart-ownership checked)
  → version marked disputed → doctor "concerns" card appears
  → Confirm (issue recorded; correction follows separately)
     or Dismiss (note required for accountability)
  → last-open resolution lifts the version flag;
     full trace kept in disputes table + audit

7.5 Discovery & scan paths

Handoff token (single-use, expiring) → redeem → request → grant
QR scan (/e/<token>) → login (context preserved via ?next=) → scoped view
Unknown token → invalid state, zero patient data
