# MediLink — Build Plan & Roadmap

A provenance-aware, consent-driven longitudinal health-record platform for India: verified doctors/labs/hospitals contribute authenticated records; patients control access; emergency clinicians get audited break-glass access; an AI layer produces clinical summaries where **every claim cites its source record**. Core promise: *"A doctor understands this patient in 5–10 seconds — and can prove where every fact came from."*

The original 68-section brief was strong on principles; this plan tightens it into an executable sequence. Key strategic corrections confirmed by research: (1) ABDM is an interoperability **target**, not a prerequisite — mock adapters now, sandbox spike later (ABDM now ships V3 APIs, M1/M2/M3 milestones, plus an official NHA wrapper repo); (2) DPDP Rules 2025 were notified 13 Nov 2025 with phased rollout to ~May 2027 (consent managers Nov 2026) — consent-first architecture now is well-timed and required; (3) doctor-first value is the wedge (every Indian PHR is patient-first; none offers record-level provenance or cited summaries — our differentiation per competitive research).

## 2. Architecture decisions (the load-bearing ones)

- **Modular monolith**: modules = auth, identity, patients, records, documents, consent, access, audit, search, ai, notifications, integrations. Clear imports-only boundaries; no premature microservices.
- **FHIR-inspired schema**: relational tables for `conditions, allergies, observations, medication_statements, procedures, immunizations, diagnostic_reports, documents(+versions)` — each carrying a `resource` JSONB column holding FHIR R4-shaped JSON (NRCES-compatible later) so interop isn't foreclosed. No single `medical_history TEXT`, no isolated proprietary model.
- **Provenance on every clinical row**: `author_id, org_id, source_document_id, signed_at, content_hash, verification_status`. Append-only amendments via `superseded_by` pointers — originals are never overwritten.
- **Identity**: internal `patient_uuid` primary; ABHA stored as a separate linked identifier via an `AbdmAdapter` (mock now). Never Aadhaar as FK.
- **Verification behind an adapter**: `VerificationProvider` interface with `Mock` (dev/demo) and `ManualReview` (admin queue) implementations; HPR/HFR sandbox adapter later.
- **Consent as data**: grants = grantee + category scopes (demographics/allergies/meds/labs/imaging/sensitive) + purpose + expiry + revoke. A single access-check layer enforces consent on **every** record read; DPDP-aligned notice/audit surfaces.
- **RAG isolation (non-negotiable)**: retrieval queries are built by one repository function that **always** injects `patient_id` + authorized-resource filter; the LLM only ever receives pre-authorized, ID-tagged chunks. Security tests prove cross-patient retrieval is impossible.
- **Citation integrity**: AI summaries persist as `ai_summaries` + `ai_summary_claims` (one row per claim, each with `source_record_ids`). Post-generation validation **drops any claim whose citations aren't in the retrieved set**. UI renders numbered citations (OpenEvidence-style) linking to source documents.
- **Contradiction engine v1**: deterministic conflict detection (blood group mismatch, allergy conflicts, duplicate reports, DOB variance) — flagged, never auto-resolved; verified sources outrank self-reported ones in display order.
- **Audit**: append-only `audit_events` with hash chaining (`prev_hash` → row hash); break-glass events trigger patient notification + review queue.
- **AI safety scope**: summarize/extract/timeline/trends/search/duplicates only. No diagnosis, dosing, or treatment output. Every AI surface labeled "AI-generated".

## 3. Product surface (MVP)

Two full portals + one simplified console (per chosen scope):
- **Patient portal**: dashboard, timeline, documents, medications/allergies, consents (grant/revoke/expiry), access history, emergency profile editor.
- **Doctor portal**: patient search (consent-aware), **Patient-at-a-Glance (SBAR-structured)**, medical timeline (LifeLines-style facets), AI summary with citations, lab trends (sparklines), document viewer, upload-with-provenance.
- **Org console (lite)**: staff list, verification status, patients served, uploads, audit view. Platform-admin: verification queue, break-glass review, user/org management — no casual clinical-data access.

## 4. Roadmap (each milestone ends in a demo-able outcome)

- **M0 — Foundation**: repo, Next.js 16 + TS + Tailwind + shadcn base, Better Auth with roles, Supabase + Drizzle core schema, Vercel deploy in `bom1`, CI (lint/type/test), seed-script skeleton. *Demo: deployed app with auth + role routing.*
- **M1 — Identity & verification**: practitioner/org registration, verification pipeline (mock + manual-review queue), org console lite. *Demo: a "doctor" becomes verified end-to-end.*
- **M2 — Records & provenance**: clinical CRUD by verified actors, document upload (presigned) + ingest v1 (store/hash/text-extract), timeline v1, amendments. *Demo: verified lab user uploads a report → appears on patient timeline with full provenance.*
- **M3 — Consent & audit**: grants/revoke/expiry, access enforcement everywhere, hash-chained audit, patient access-history, in-app notifications. *Demo: doctor blocked → patient grants → doctor reads → patient sees the access entry.*
- **M4 — Intelligence**: OCR/LLM structured extraction (Zod-validated), contradiction engine, hybrid patient-scoped search, RAG summary with claims+citations, sparkline trends, SBAR glance. *Demo: "Summarize this patient's cardiac history" → cited, verifiable answer.*
- **M5 — Emergency**: emergency profile, break-glass flow (reason mandatory, time-boxed, audited, patient notified), review queue. *Demo: unconscious-patient scenario in <10s.*
- **M6 — Golden demo & hardening**: full 16-step golden path as Playwright E2E, synthetic dataset (~30 patients/500+ dirty documents: conflicts, duplicates, Hindi, poor scans), security suite (cross-patient/org isolation, revoked/expired consent, break-glass audit), responsive + a11y + Vercel-guidelines audit, DPDP checklist doc. *Demo: the definition-of-done scenario, green.*
- **M7 — Marketing site + ABDM spike (time-boxed)**: art-directed public site per the original design brief (design → structure → build → motion → screenshot review → audit, using `docs/design-principles.md`); ABDM sandbox exploration (V3 APIs, ABHA link adapter) if time allows.

## 5. Design direction (applied at build time)

Follows the studied skills: ground everything in the subject's world (paper trails, lab reports, chart annotations, medical stamps) — **not** generic AI-SaaS styling; no purple gradients/glassmorphism/glowing blobs. Typography-led identity with deliberate pairing; one signature element (leading candidate: the interactive **citation/provenance chain** — click any fact, see its source chain). Motion budget: page-load orchestration on the marketing hero, one scroll-reveal system, surgical micro-interactions; `prefers-reduced-motion` respected throughout.

## 6. Top risks & mitigations

- **LLM hallucination** → claim-level citation validation + "AI-generated" labeling + contradiction flags.
- **Free-tier limits** (Supabase/Inngest/Gemini) → usage monitoring; upgrades budgeted.
- **ABDM V3 API flux** → integration isolated in adapters; sandbox spike before any dependency.
- **Name collision ("MediLink" is a common health-IT name)** → proceed as working title; trademark/domain check before public launch.
- **Medical-legal exposure** → AI scope limits, disclaimers, legal review before real-patient data (never real data during development — synthetic only).

## 7. Definition of done

The brief's §68 scenario passes as automated E2E: patient created → verified org → verified doctor → authenticated records uploaded → originals preserved → structured extraction → timeline → consent granted → second doctor authorized → history + AI summary with citations → citations open sources → break-glass works → audit logs everything → patient sees access history. Plus: mobile-responsive, keyboard-navigable, contrast-checked, and deployed on Vercel Mumbai.
